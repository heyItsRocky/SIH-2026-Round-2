# SIH 2026 Problem Selection Framework

> Master evaluation framework for SIH 2026 Round 2 problem selection.
> This document is the stable scoring model — it should remain relatively unchanged.

---

## 1. Evaluation Criteria

### 1.1 SIH Official Rubric (multi-year, cross-verified)

| Criterion | Weight | Notes |
|---|---|---|
| Novelty / Innovation | High | Is this genuinely new, or a rehash? |
| Complexity / Technical Depth | High | Does it require real engineering, not CRUD? |
| Clarity / Problem Understanding | Med | Do we understand the actual problem? |
| Feasibility / Practicability | High | Can we build it in the hackathon window? |
| Sustainability | Med | Would it survive past the demo? |
| Scale of Impact | Med | How many people does it help? |
| UX / Presentation | Med | Is the demo compelling? |
| Future Progression | Low | Could it grow into a real product? |

**Additional rubric axis (SIH 2025 internal-round):** Preparedness / Past Work — GitHub, prior competition record. ULTRON already built = free points.

### 1.2 Team-Specific Criteria

| Criterion | Description |
|---|---|
| Problem Quality | Is the problem real, severe, and well-scoped? |
| Competition Density | How many teams will pick this? (lower = better) |
| Solution Convergence | Will most teams build the same thing? |
| Hidden Constraints | Is there a non-obvious differentiator? |
| Existing Solutions | Is the space saturated or genuinely open? |
| Tech-Stack Difficulty | Intrinsic difficulty of the required stack |
| Team-Adjusted Difficulty | Difficulty given our actual skills |
| ULTRON Advantage | Does our hardware give us a real edge? |
| Data Risk | Can we get the data we need? |
| Execution Risk | Can we finish in the window? |
| Deployment Risk | Is there a real adoption path? |
| Scalability | Can it grow from prototype to pilot to scale? |
| Judge Factors | Will judges understand and be impressed? |
| Differentiation | Is our approach meaningfully different? |
| Why-Us Factor | Why would the sponsor adopt OUR solution? |

## 2. Anti-Patterns (what to avoid)

| Anti-Pattern | Description |
|---|---|
| "Sounds impressive" trap | Choosing a problem because it sounds futuristic, not because it's buildable |
| Hardware costume | Bolting ULTRON onto a software problem where it adds nothing |
| Hardware trap | Forcing hardware into a problem that explicitly doesn't need it |
| Crowded giant | Picking a problem everyone will build the same answer to |
| Blockchain theatre | Leading with a buzzword instead of the actual engineering |
| Overclaiming | Claiming validated science we don't have (e.g., "we predict cave-ins") |
| Scope creep | Trying to solve all of a multi-part problem instead of one deep slice |

---

## 3. Scoring Formula

```
Strategic Value ∝ (Impact × Differentiation × Team Advantage × Demo Potential)
                ÷ (Competition × Team-Adjusted Tech Difficulty × Execution Risk)
```

---

## 4. Decision Workflow

```
Problem
  ↓
Reality (research)
  ↓
Existing solutions
  ↓
Gap
  ↓
Expected competition
  ↓
Tech stack
  ↓
ULTRON fit
  ↓
Differentiation
  ↓
Prototype
  ↓
Final decision
```

**Do not start coding until the problem, reality, existing solutions, gap, competition, tech stack, ULTRON fit, and differentiation are all established.**
